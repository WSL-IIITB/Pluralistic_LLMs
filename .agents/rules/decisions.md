## 2026-09-06 — yt-dlp as a YouTube comment source (evaluation)
**Context:** Asked to evaluate whether yt-dlp (https://github.com/yt-dlp/yt-dlp) can be integrated to source YouTube comments instead of / alongside the current YouTube Data API v3 connector (`YouTubeConnector` in backend/app/connectors/sources.py). Today YouTube is sourced via `googleapiclient`: `search.list` (flat 100 quota units/call, maxResults 25, regionCode="IN") + `commentThreads.list` (1 unit/call, maxResults 100, top-level comments only), gated on `YOUTUBE_API_KEY`, invoked per-framing (3–10 depending on mode) and per-state in extrahigh mode (36 states → 3,600 units on top of the framing searches). Quota exhaustion is already the dominant real-world failure mode and has dedicated handling in `source_posts` (`_is_quota_exceeded`, user-facing "quota exhausted" status event). The `SourceConnector.search(query, limit)` protocol in backend/app/connectors/base.py is the frozen seam the graph talks to — no graph code touches the transport.
**Decision:** Recommend a HYBRID integration — keep the Data API for the search stage (reliable, native `regionCode="IN"` geo-targeting, flat 100-unit cost), use yt-dlp ONLY for comment harvesting (no quota, unlocks the reply-thread data the API path drops). Gate the transport behind a new `youtube_provider=api|ytdlp` setting (default `api`) while keeping the existing env-gated factory `get_youtube_connector()` shape, so both transports remain testable. **No code written yet — recommendation pending go-ahead.**
**Why:** (a) Eliminates the 10k/day quota ceiling — the biggest current failure mode that exhausted quota in practice under extrahigh runs; (b) upgrades data quality — full comment tree incl. replies, richer per-comment metadata; (c) drops in behind the existing `SourceConnector` protocol, so zero LangGraph/pipeline changes; (d) keeping the API for search retains geo-targeting a bare `ytsearch` scrape can't express.
**Alternatives Considered:** (1) Full swap to yt-dlp for search + comments — rejected: loses `regionCode` geo-filtering, slower per call, and scraping under the 6-way-concurrent fan-out risks rate-limit/CAPTCHA blocks; (2) keep API entirely as-is — rejected: daily quota keeps getting exhausted by the extrahigh per-state pass.
**Open risks (accepted, internal/research tool):** scraping YouTube violates ToS and yt-dlp itself has faced DMCA takedowns; yt-dlp needs frequent updates as YouTube's internals drift; no native per-state geo filter on comments (mitigated by the query-suffixing the per-state pass already uses).

## 2026-09-06 — yt-dlp CONNECTOR IMPLEMENTED; all-yt-dlp SUPERSEDES the hybrid
**Context:** The live smoke test corrected the earlier hybrid's quota math — `search.list` is the expensive 100-unit call, comment harvesting is only 1 unit — so "API search + yt-dlp comments" would have fixed the cheap half and left the daily-quota failure mode fully intact. The smoke test also proved no-cookie **search** works, so dropping the API for everything is viable.
**Decision:** Implemented `YouTubeDlpConnector` in backend/app/connectors/sources.py doing BOTH search (`ytsearchN:{query}`) and comment harvesting (`getcomments` constructor option) via yt-dlp. Selected by new `Settings.youtube_provider` = "ytdlp" (default stays "api"); `get_youtube_connector()` branches to it FIRST because it needs no credentials. Zero LangGraph changes — the `SourceConnector` protocol is unchanged. Validated live through the actual connector object (150/60/22 SourcedPosts for bare-topic / per-state-suffix / policy queries; all shapes correct).
**Why:** Eliminates the entire YouTube quota dimension (the dominant failure mode), includes reply threads the API path drops, needs no key — all behind the existing frozen seam.
**Alternatives Considered:** (1) hybrid API-search + yt-dlp-comments — rejected after the smoke test corrected the cost math; (2) Data API + yt-dlp only for extra reply harvesting — more code, search still quota-bound; (3) keeping the API unchanged — rejected (recurrent quota exhaustion).
**Implementation findings (re-verify on yt-dlp upgrades):** `getcomments` is an extract_info() TypeError on 2026.08.x unless set as a constructor option; a single dead ytsearch entry aborts the whole extract_info without `ignoreerrors: True`; skipped entries then appear as None in the entries list (must filter). ~5/25 live "Diwali" hits were "video not available" — anonymous-scrape tolerance, absorbed by ignoreerrors. yt-dlp deprecation-warns Python 3.10 (works; move venvs to 3.11+ eventually).
**Trade-offs still to characterize in a full-pipeline run:** ~5-7s per search + per video-crawl vs the API's sub-second calls (extrahigh ≈ 46 searches × that, through the 6-wide semaphore); limit=150 filled from only 2 videos (100-comment/video cap fills fast) — narrower per-search video diversity than the API path.

## 2026-09-06 — yt-dlp SOURCING LATENCY MEASURED; extrahigh too slow as-is, speedup path identified
**Context:** Full-pipeline charactersation was the open item left by the connector work. No LLM backend exists on this machine (no OPENAI/Azure/gemma endpoint, and the heavy venv — torch/chromadb/sentence-transformers — isn't installed and the LLM stages don't depend on the YouTube connector), so the yt-dlp-DOMINATED portion — the sourcing stage — was measured directly through the REAL `source_posts` node (graph/build.py) with the real `YouTubeDlpConnector`, at each mode's real fan-out shape (framing searches; extrahigh adds the per-state pass, 32 states in STATE_PRIORITY_ORDER), using a minimal deterministic stub LLM (_MeasureLLM: realistic framings + keep-all relevance, in the measure script). Diwali, real live YouTube, no key/cookies.
**Decision:** **yt-dlp default for basic/medium/high is a clear net win; extrahigh needs two speedups before all-yt-dlp is viable there.** Measured sourcing wall-clock: basic(3) 49 posts/7 videos/66.9s; medium(5) 210/6/55.2s; high(8) 848/24/121.1s; extrahigh(42) 1427/70/374.0s. | Diversity is GOOD at full fan-out (70 distinct videos, 20 posts/video mean at extrahigh) — the earlier "150 from 2 videos" worry applies mainly to shallow/single-search runs. | 30-35% of harvested comments are low-signal (<4 Unicode words) and dropped by `_is_low_signal`, i.e. wasted crawl. | same dead video IDs recur across different framing searches — each costs retries.
**Why:** (a) The quota dimension is gone entirely for the modes most users actually run, at an acceptable wall-clock (1-2 min sourcing). (b) extrahigh at 374s of pure sourcing is the clear breaking point, and most of that is throwaway crawl (dead-video re-crawls + low-signal comment bulk), so the fix is cheap rather than structural.
**Proposed speedups (FIX ORDER):** (1) `_ytdlp_client` already passes `extractor_args.youtube.max_comments` — lower 100→50: halves crawl time while yield barely drops (pipeline drops most of the 2nd 50 anyway). (2) Per-run seen-set of failed/skipped video IDs consulted before each crawl — ~15-20% of IDs are dead and recur; skip them + skip `None` entries instantly. Both are sunk inside `YouTubeDlpConnector` (the SourceConnector seam + graph untouched). Re-measure after.
**Alternatives Considered:** (1) keep API default + yt-dlp only as opt-in — fine for now, but unfair to the common modes; (2) raise `_MAX_CONCURRENT_FETCHES` 6→12 — rejected: risks YouTube rate-limit/captcha walls, and the wall-clock is retry/crawl-bound not search-bound, so more concurrency helps little; (3) filter low-signal comments inside the connector — rejected for now: `_is_low_signal` already drops them right after sourcing, a connector-level filter duplicates logic and risks dropping text the pipeline wants; the real lever is the max_comments reduction.
**Open:** true full end-to-end run (LLM stages on top) still unmeasured — needs an LLM key/endpoint + the heavy venv.

## 2026-09-22 — Repo requires Node 22+; global Node 20 can't run vite dev
**Context:** `vite dev` (Vite v8.2.0, rolldown) crashes instantly on this machine's global Node v20.10.0 with `SyntaxError: The requested module 'node:util' does not provide an export named 'styleText'` (`formatWithOptions`/`styleText` are Node 20.6/22+ APIs). The lockfile diff (only an added `lru-cache` entry) rules out a version bump — vite 8 always required Node ≥22.
**Decision:** Keep the global Node v20.10.0 intact and run the frontend with a **portable Node v22.23.2 LTS** extracted to `%LOCALAPPDATA%\Programs\Node22\node-v22.23.2\` (npm 10.9.8). Invoke vite DIRECTLY with that node: `<portable-node>\node.exe node_modules/vite/bin/vite.js dev` — `npm run dev` must NOT be used, because npm's `.cmd` shim prepends its own (global, v20) dir to PATH and re-crashes the build.
**Why:** Least invasive path — no system install, no PATH change, fully reversible (delete the folder); the machine's other projects keep their Node 20. The npm.shimgotcha means the launch recipe must be documented, not left as "npm run dev".
**Alternatives Considered:** (1) `winget install Node.js.LTS` globally — rejected (touches other projects' runtime, requires admin, no clean rollback); (2) fnm/nvm-windows — rejected (extra tool install for a one-time need; the portable zip does the same thing with zero state).

## 2026-09-22 — NITI Aayog has NO direct integration; it exists only as an LLM prompt bias
**Context:** Asked whether NITI Aayog data is used anywhere in the pipeline. Grep of the whole repo found no NITI Aayog connector, API client, dataset, or niti.gov.in fetch anywhere — the only hits in project code are prompt strings, docstrings, and type comments.
**Decision:** Conclusion: NITI Aayog is currently a *named source preference*, not a data source. The one functional reference is `_OFFICIAL_SOURCE_BIAS` in backend/app/connectors/llm.py (lines 56-65) — a prompt string shared by every research `_research_one()` call (OpenAI/LocalOllama/RemoteGemma) instructing the LLM's web search to prioritize NITI Aayog (niti.gov.in), data.gov.in, PIB, *.gov.in, Census/NSSO/NFHS/UDISE+/RBI, and parliamentary replies. Whatever the LLM search returns flows: ResearchDocument → (research.py `_posts_from_research_documents`) → RawPost(platform "research") → same geo-resolution + clustering as social posts, cited by the synthesis stage. If a niti.gov.in page is returned, it's because the search engine found it — nothing fetches NITI Aayog directly. (The `NITI` hits in sources.py/reasoning_modes.py were "in**iti**al" false positives.)
**Why:** Sets expectations for any "official data" work: adding real NITI Aayog / data.gov.in sourcing would be a NEW connector behind the `SourceConnector` seam (or a dataset ingestion + vector store), not a config flip. The current official-source "integration" is prompt softness only — the model can find official pages, but nothing guarantees them.

## 2026-09-06 — yt-dlp is now the default YouTube provider
**Context:** The sourcing latency measurement concluded yt-dlp is a clear win for basic/medium/high, with extrahigh as the only fast-risk (374s sourcing, speedup plan above). The user decided: make yt-dlp the default now; it can be flipped back with one config line anytime.
**Decision:** `Settings.youtube_provider` default changed `"api"` → `"ytdlp"` (config.py). `.env.example` `YOUTUBE_PROVIDER=ytdlp` + comment updated; backend/README.md "optional" subsection rewritten as "default" (API path documented as opt-in fallback via `YOUTUBE_PROVIDER=api`). Verified: factory now returns `YouTubeDlpConnector` with no env present.
**Why:** Removes the quota dimension for every typical run by default; no key needed; the API path remains fully selectable per-deployment, and the source can be flipped back (or made conditional on mode) in one line whenever the extrahigh speedups are re-measured — defaulting is cheap because the seam (`get_youtube_connector`) makes reversal trivial.
**Note:** the API path was NOT removed — `YOUTUBE_PROVIDER=api` + a `YOUTUBE_API_KEY` returns to it unchanged. The speedup work in the prior entry is still the recommended next step before trusting extrahigh on the new default.

## 2026-09-22 — NITI /niti CSVs become a first-class source behind the SourceConnector seam
**Context:** User wants the app to answer from REAL data (the two `/niti` CSVs, ~776 districts each) via a FastAPI endpoint, streaming the full worldview answer, plus the app itself flipped live. Constraint: later sources (YouTube/Reddit real) must add with minimal code change.
**Decision:** New `NitiCsvConnector` in `connectors/sources.py` implementing the EXISTING `SourceConnector.search(query, limit)` Protocol — new no-pipeline-coupling source #3. `platform="niti"` (Literal extended in schema.py + types.ts). Scoring: query tokens vs state (+5) / district (+7) / indicator-column names (+4); state ROUND-ROBIN interleaving so results span India; post text renders `"District, State — indicator value [%]"` so geo-resolution sees the district/state names literally. `settings.csv_data_dir` (default `REPO_ROOT/niti`) + `has_niti_csv` gate the factory. NO stub variant on purpose. `source_posts` runs one `fetch_csv(framing)` per framing in the existing gather.
**Why:** (a) The connector seam is the frozen contract — adding CSV needed ZERO LangGraph topology changes, exactly the "later sources are cheap" property the user asked for; switching a future real YouTube/Reddit connector in is the same shape of work (a factory branch). (b) Round-robin mirrors the pipeline's per-state fan-out philosophy without inventing a second fan-out dimension. (c) The underlying data is curated stats — an LLM yes/no relevance judge on it is redundant (and, under the fail-closed stub, destructive), so `_STRUCTURED_SOURCE_PLATFORMS={"research","niti"}` skips the relevance gate for them, matching how research documents were already exempted.
**Alternatives Considered:** (1) A separate CSV-specific pipeline branch — rejected: it would fragment the source abstraction the whole design rests on. (2) Reusing platform="research" for CSV rows — rejected: can't tell a statistics row from a web-sourced document in the UI, and "niti" is the honest label. (3) A stub CSV connector for zero-data machines — rejected: fabricating government statistics contradicts the stub philosophy (stubs mimic *demo content*, never authoritative data); a missing folder contributes zero posts instead.

## 2026-09-22 — gemma_remote without a base_url now falls back to the stub LLM when ALLOW_STUB_FALLBACK=true
**Context:** The frontend defaults to `provider=gemma_remote`, and `get_llm_client` previously constructed `RemoteGemmaLLMClient` unconditionally for it — which RAISES `RuntimeError` when `REMOTE_GEMMA_BASE_URL` is unset (it has no default, on purpose). So a zero-credential box (this machine) could not run the backend at all once the app flips live, even though "stub fallback" is the designated offline mode.
**Decision:** In `get_llm_client`, the `gemma_remote` branch now returns `RemoteGemmaLLMClient(settings)` only when `settings.has_remote_gemma`; without a base_url it returns `StubLLMClient()` if `ALLOW_STUB_FALLBACK=true`, else raises a clear RuntimeError. Also documented Google Gemini's OpenAI-compatible endpoint (`https://generativelanguage.googleapis.com/v1beta/openai/`) as a valid `REMOTE_GEMMA_BASE_URL` in .env.example, since the user noted Gemini gives free credits.
**Why:** Keeps the honest-zero-credentials contract (raise, don't silently degrade) when stub fallback is OFF, while letting the documented stub mode actually be usable with the app's DEFAULT provider. Provider-selection semantics stay: real provider if reachable, stub only under explicit opt-in.
**Alternatives Considered:** (1) Change the frontend's default provider — rejected, that would misrepresent what a keyless user gets. (2) Set a fake RemoteGemma base_url — rejected as a lie in config. (3) Leave it raising and make the user hand-edit provider per call — rejected, blocks the "flip the app to live" milestone.

## 2026-09-22 — Backend venv: light-core install for stub-mode; heavy LLM stack deferred
**Context:** The backend's `requirements.txt` pulls `sentence-transformers` (→ torch, multi-GB), `chromadb` (+onnxruntime). This machine has only Python 3.10 and no existing backend venv. Grep showed the heavy imports are ALL function-local (`llm.py:161`, `region_kb.py:95`, `research_cache.py:66`), while numpy/scipy/scikit-learn are top-level (cluster_viewpoints, infer_regions, dataview) and thus required at boot.
**Decision:** `backend/.venv` installs the light core only: fastapi, uvicorn[standard], sse-starlette, pydantic(-settings), langgraph, openai, anthropic, httpx, praw, google-api-python-client, yt-dlp, numpy, scipy, scikit-learn, openpyxl. The heavy stack is deferred until a real LLM path (Gemini key / OpenAI / internal server) is configured — then `pip install -r requirements.txt` completes the venv. Stub-mode runs never touch torch/chromadb (stub embed is hash-based, research returns empty).
**Why:** Torch is a ~2.5 GB+ download for a code path that is thoroughly lazy and unused in the milestone's stub mode; installing it now buys nothing and risks a long/failing install derailing the deliverable. The two-tier install is documented (decisions.md + context.md) so nobody mistakes the light venv for the full one.
**Alternatives Considered:** (1) Full `requirements.txt` now — rejected (multi-GB, unused in stub mode). (2) Reuse `scripts/.smoke-venv` — rejected (wrong purpose, missing langgraph/fastapi). (3) System pip install — rejected (no admin, pollutes machine).

## 2026-09-22 — Structured-platform rows also bypass the low-signal word-count gate
**Context:** End-to-end checks showed `kept_platforms={'niti': 18}` when the CSV cap was 25 for a query like "dropout" under stub mode. The 8 lost CSV rows were NOT relevance drops — they were low-signal drops. `_is_low_signal` requires ≥4 Unicode word tokens, and `_WORD_RE = \w{2,}` does NOT count single-digit tokens, so a short but perfectly valid stats row like `Delhi, Delhi — dropout_rate 8.9%` tokenizes to 3 words ("delhi delhi dropout_rate" — "8" and "9" are length-1) and was dropped as noise.
**Decision:** In `source_posts`, rows whose platform is in `_STRUCTURED_SOURCE_PLATFORMS` now bypass the low-signal gate too (`if p["platform"] not in _STRUCTURED_SOURCE_PLATFORMS and _is_low_signal(...)`), with a comment explaining the digit-tokenization case.
**Why:** The gate exists to stop emotive social chatter with no stance from reaching clustering. A curated indicator row was never the target, and the underlying data is authoritative stats — dropping it because the district/state happen to be short is purely harmful. The CSV path is already exempt from the relevance gate for the same reason; this closes the parallel hole. Verified: both test queries now keep the full 25.
**Date/context:** 2026-09-22, end-to-end NITI verification session.

## 2026-09-22 — Stub-LLM mode skips the entire social (reddit/youtube) crawl
**Context:** The app flipped live; a real UI query (`mode=medium`, `provider=gemma_remote`) took ~50s — 5 framing searches, each firing a live anonymous yt-dlp YouTube comment crawl. But under the stub LLM the relevance judge fails CLOSED, so every social post is deterministically dropped before clustering (logs: 243 off-topic drops, kept_platforms always `{'niti': N}`). The entire crawl was throwaway wall-clock.
**Decision:** `source_posts` now detects `isinstance(llm, StubLLMClient)` and, in stub mode, skips the reddit fan-out, the per-framing youtube crawls, and extrahigh's per-state youtube pass — sourcing runs CSV passes only. Logs one explicit "skipping social crawl" line so the run never looks mysterious. When a real LLM is configured (Gemini key / OpenAI / internal), `StubLLMClient` is no longer the client and the crawl returns automatically.
**Why:** (a) Bit-for-bit identical final answer in stub mode — the dropped social posts contribute nothing, so skipping them is semantically free. (b) Since-verified latency: same medium query went ~50s → 0.8s (17 districts, 6 clusters, 6 deflections, full answer). (c) No config flag or new seam — keyed off the actual active client, which is the single honest source of truth for "will relevance filtering do anything."
**Alternatives Considered:** (1) Leave it slow — rejected, the user's live query experience was the whole point of the milestone. (2) Gate on `settings.allow_stub_fallback` — rejected: that setting says stub MAY be used, not that the stub IS the constructed client; a future auto-select between real/stub would desync the gate from reality. (3) Filter out social posts earlier instead — would produce identical waste; the crawl is the cost, not the filtering.
**Date/context:** 2026-09-22, immediate follow-up to the live-app flip.
